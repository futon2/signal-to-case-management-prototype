# 経営論点・予兆管理システム プロトタイプ

英語名: Signal-to-Case Management

会社の中で発生している小さな違和感・懸念・予兆を「シグナル」として軽く集め、その中から上位層が見るべきものを「要注意シグナル」として可視化し、必要なものだけを正式な「案件」として厳格管理する説明用プロトタイプです。

## 起動方法

ビルドやインストールは不要です。

1. `index.html` をブラウザで開く
2. 左ナビゲーションから画面を切り替える
3. 入力データはブラウザの `localStorage` に保存される
4. 初期状態に戻す場合は画面右上の「データ初期化」を押す

Python が PATH にある環境で、ローカルサーバから開きたい場合の例:

```powershell
cd C:\Users\takah\Documents\Codex\signal-to-case-management-prototype
python -m http.server 5173
```

その後、ブラウザで `http://localhost:5173` を開いてください。

## シグナル、要注意シグナル、案件の定義

### シグナル

現場の小さな違和感、懸念、兆し、気づきです。正式な課題や案件でなくてよく、入力負荷を低くします。

### 要注意シグナル

シグナルのうち、幹部メンバー、本部長、管理職がウォッチすべき重要な兆候です。正式な案件ではありませんが、放置すると案件化・問題化する可能性があります。

### 案件

責任者、期限、金額、対応方針、報告先を持つ正式な管理対象です。案件化後はシグナル段階より厳格に管理します。

基本メッセージ:

```text
入口は軽く、重要なものだけ要注意化し、案件化したらしっかり管理する。
```

## プロジェクト型案件と定型業務型案件の違い

### プロジェクト型案件

システム開発やITインフラ整備など、複数年・高額になりやすい案件です。常時40〜50件程度の案件群を俯瞰する想定です。

主な状態軸:

- 進捗
- 採算
- 品質
- 要員
- 顧客

### 定型業務型案件

予算策定、決算、監査、親会社提出資料など、比較的定型化された業務案件です。金額よりも納期遵守、工程管理、承認、関係者回答が重要です。

主な状態軸:

- 期限
- 工程
- 承認
- 回答
- 品質

## データモデル

型定義は [types.ts](./types.ts) に記載しています。

主なモデル:

- `Case`: 案件の共通情報
- `ProjectCaseDetail`: プロジェクト型案件の詳細
- `RoutineCaseDetail`: 定型業務型案件の詳細
- `Signal`: シグナル、要注意シグナルの情報
- `CaseStatusHistory`: 週次一言更新などの状態履歴

## 週次一言更新の考え方

案件の定期更新は、毎回すべての項目を入力させません。前回値をコピーし、変化がある項目だけを最小入力で更新する想定です。

入力項目:

- 総合状態: 正常 / 注意 / 危険
- 前回からの変化: 改善 / 横ばい / 悪化
- 一言コメント
- 必要な支援: なし / 要員 / 顧客調整 / 経営判断 / 予算 / その他

登録後、疑似AIが以下を提示します。

- AI要約
- 推定される状態軸の変化
- 要注意シグナル候補
- 推奨報告先
- 次に確認すべきこと

## 疑似AI処理

実際のAI APIは使っていません。`app.js` 内の関数で疑似的に処理しています。

### カテゴリ推定

入力文に含まれるキーワードから以下を推定します。

- 採算、赤字、利益、工数超過、追加見積: `profitability`
- 仕様変更、要件変更、前提変更、見積: `estimate`
- 不具合、障害、品質、手戻り、テスト: `quality`
- 納期、遅延、スケジュール、期限: `schedule`
- 要員、人手不足、兼務、負荷集中、PM不足: `staffing`
- 突発休、休職、疲弊、気分、体調: `organization`
- 出社、在宅、テレワーク、座席、相談機会: `hybrid_work`
- 顧客、クレーム、承認遅れ、反応が悪い: `customer`
- 承認、滞留、決裁: `approval`
- 提出、親会社、締切、未提出: `deadline`

### リスクスコア

- 深刻度が高い: +30
- 深刻度が中: +15
- 発生頻度が繰り返し: +20
- 発生頻度が時々: +10
- 採算、顧客、組織、期限、承認カテゴリ: +20
- 遅延、赤字、休職、障害、未提出、承認滞留、幹部会などのキーワードあり: +20
- 関連案件がある: +10

スコア判定:

- 0〜39: 通常シグナル
- 40〜69: ウォッチ
- 70〜84: 要注意シグナル
- 85〜100: 案件化候補

## 初期版と最終形の違い

| 項目 | 初期版 | 最終形 |
| --- | --- | --- |
| データ入力 | 手入力中心 | 手入力＋既存システム連携 |
| AI機能 | 疑似AI | 本物のAI分類・要約・類似検出 |
| シグナル | 手入力 | 勤怠、座席、会議資料、工数、気分登録から自動検知 |
| 要注意シグナル | リスクスコアで疑似判定 | AIとルールで自動抽出 |
| 案件管理 | ダミーデータ中心 | 実案件・実ステータスと連携 |
| 案件タイプ | プロジェクト型・定型業務型を表現 | 実業務テンプレートと連携 |
| 状態推移 | ダミー履歴 | 月次・週次スナップショット |
| 導入範囲 | 1〜2部門 | 全社 |
| 目的 | 仕組みの理解 | 全社の予兆管理・経営可視化 |

## 本番化する場合の拡張ポイント

- 勤怠システムとの連携
- 座席管理システムとの連携
- テレワーク・出社データとの連携
- 工数管理との連携
- 案件管理・原価管理との連携
- 会議資料、Excel、PowerPointからのAI抽出
- Microsoft 365、Teams、SharePointとの連携
- 気分登録機能の追加
- Azure OpenAIまたはOpenAI APIによる本物のAI分類
- AIによる要注意シグナル自動抽出
- AIによる幹部会向けサマリー生成
- Power BIとの連携
- 権限管理
- 個人情報・健康情報の取り扱いルール
- 人事評価には使わない明確な方針
- 本部長、人事、産業保健、経営層で閲覧範囲を分ける設計

## 注意事項

このプロトタイプは、従業員を監視するためのものではありません。

- 目的は監視ではなく早期支援
- 個人を責めるためではなく、組織課題を早く見つけるため
- 評価・査定には使わない
- 個人情報・健康情報は本番化時に閲覧権限を厳格にする
- 最初は個人単位ではなく、チーム・課単位の傾向把握を重視する

## 技術メモ

ローカルで確実に動くことを優先し、依存なしの静的 HTML/CSS/JavaScript で作成しています。React + TypeScript + Vite に移行する場合は、`types.ts` の型定義をそのまま使い、`app.js` 内のデータ生成、疑似AI、描画処理をコンポーネントとサービス層へ分割してください。
